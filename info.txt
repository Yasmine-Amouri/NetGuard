2)ADR-001 — What exactly is an event?
Yes! In our example, an event is a piece of information representing something that happened at a particular time.

For NetGuard, let's say a network link is monitored and produces these measurements:
Timestamp	RTT	Jitter	Packet loss
10:00:00	35 ms	2 ms	0%
10:00:01	42 ms	3 ms	0%
10:00:02	180 ms	25 ms	4%

We could represent each row as an individual telemetry event.

For example:
{
  "event_id": "evt-001",
  "link_id": "link-01",
  "timestamp": "2026-11-16T10:00:02Z",
  "metrics": {
    "rtt_ms": 180,
    "jitter_ms": 25,
    "packet_loss": 0.04
  }
}


So, in our current design:
- One event = one telemetry measurement for one network link at one point in time.
- The collector generates or retrieves these measurements.
- The collector publishes them to the next component.
- The processor consumes them.
Important distinction: generating an event doesn't necessarily mean sending it directly to the processor. It means creating the event. How it gets delivered depends on our communication architecture.

Also, later we might publish other kinds of events, such as anomaly.detected or incident.created. So an event is a general concept, not just a measurement.

Telemetry is data collected from a system to monitor its behavior, performance or condition.

In NetGuard, we're interested in network telemetry.

For example:
Metric	What it measures

Jitter	Variation in packet delay

4)But now you need to implement several things:
- How does the processor claim an event so another processor doesn't process it simultaneously?
- How do you handle a processor crash halfway through?
- How do you retry failed events?
- How do you prevent two processors from updating the same event?
- How do you clean up old records?
- How do you let multiple independent services consume the same event stream?
These problems are solvable with PostgreSQL, but you're building a messaging system on top of a general-purpose database.


One particularly useful Kafka feature is consumer groups.

Imagine NetGuard eventually needs two independent services to consume the same telemetry:
- A persistence worker stores measurements in PostgreSQL.
- An ML worker analyzes measurements for anomalies.
With Kafka, they can each have their own consumer group and independently read the same events.

The persistence worker doesn't have to wait for the ML worker. They can progress independently.

That's a major architectural advantage for NetGuard.

One important caveat: Kafka doesn't magically guarantee that every event is processed exactly once by your entire application. Consumers can sometimes process an event again after a failure. That's why we'll later discuss at-least-once delivery and idempotency.

Each group tracks its own progress. For example, the ML worker can be behind the persistence worker without preventing it from progressing.

One subtlety: within a consumer group, Kafka distributes partitions among consumers. Independent consumer groups, however, each get their own view of the topic.

This is called loose coupling: services don't need to know about each other to receive the same data.

6)2. One architectural detail to understand before moving on
There's an important concept hidden in this ADR: at-least-once delivery.

Suppose:
1. The ML worker reads event evt-001.
2. It processes the event successfully.
3. It crashes before committing its Kafka offset.
4. It restarts and reads evt-001 again.
The same event may be processed twice!

That's why we need idempotency: processing the same event more than once should not produce duplicate or incorrect results.

We'll explore this when implementing the consumers, not now.

10)1. Why not use only synthetic data?
You said:
We want to be able to detect real anomalies.

Exactly.

Imagine we build a simulator that generates data like this:
Scenario	RTT	Packet loss
Normal	30 ms	0%
Anomaly	500 ms	40%

We train our ML model on thousands of these generated measurements.

The model might learn that:
- RTT above 400 ms is abnormal.
- Packet loss above 30% is abnormal.
But real networks are more complicated. Our simulator might not reproduce their actual behavior.

For example, real network degradation could involve:
- RTT increasing gradually.
- Jitter increasing while packet loss remains low.
- Traffic increasing before latency starts rising.
- Different behaviors depending on the network link.
The danger is that our model learns the patterns of our simulator, rather than the patterns of real networks.

This is called a generalization problem.

That's why historical data is valuable: it gives us observations of real network behavior.

11)So the same measurement can have different meanings depending on context.

There are several dimensions to consider:
- Magnitude: How large is the measurement?
- Baseline: What is normal for this particular network?
- Duration: Is it a temporary spike or a persistent problem?
- Correlation: Are RTT, jitter and packet loss changing together?
For example, an RTT of 150 ms might be perfectly normal for one connection but abnormal for another.

This is why anomaly detection is interesting: we want to identify unusual behavior, not simply apply fixed thresholds.

12)This is called a sim-to-real gap: the difference between the behavior represented by our simulated data and actual real-world behavior.
What can we legitimately claim?
Experiment	What it demonstrates
Train and test on synthetic data	The model can recognize patterns in our simulator
Train on historical + synthetic, test on unseen historical data	The model generalizes to some unseen real observations
Test on real-world data from different conditions	Stronger evidence of real-world generalization

Even the last one doesn't guarantee detection of every possible failure.

14)2. Why not create dozens of microservices?
You said overengineering. Let's identify its practical consequences:
- Deployment complexity: more services to build, configure and deploy.

20)1. Scaling: Docker vs Kubernetes
One small correction: Docker and Kubernetes aren't equivalent here.
- Docker provides the container runtime: it runs containers.
- Docker Compose lets you define and run multiple containers, and supports manually scaling certain services.
- Kubernetes provides orchestration: it can automatically scale workloads based on configured metrics, restart failed containers, and manage their desired state.
For example, if your ML worker needs three instances instead of one, Kubernetes can manage that independently of your API and collector.

21)One important architectural lesson: health checks don't magically fix every failure. For example, if Kafka is temporarily unavailable, we shouldn't necessarily restart the entire Stream Processor repeatedly. We need to distinguish between an application that is dead and one that is temporarily unable to reach a dependency.

That distinction will matter when we design NetGuard's resilience.

22)1. Stopped vs. unhealthy container
First, a container is an isolated environment in which your application process runs.

There are two different situations:

Situation A — The container stops

Imagine your FastAPI application crashes because of an unhandled exception.
- The main application process exits.
- The container stops.
- Docker detects that it stopped.
- With restart: unless-stopped, Docker restarts it.
Situation B — The container is unhealthy

Imagine your FastAPI application is still running, but it gets stuck:
- The process hasn't exited.
- The container is still running.
- However, its /health endpoint no longer responds successfully.
- Docker marks the container as unhealthy.
With Docker Compose's normal restart policy, this unhealthy status alone does not trigger a restart.

23)2. What's a probe?
A probe is a check Kubernetes periodically performs to determine the state of an application running inside a container.

1. Startup probe
Has it started?
Kubernetes asks: "Has the application finished initializing?"

Useful when an application takes 30 seconds to start. Kubernetes won't prematurely consider it unhealthy while it is still initializing.


2. Liveness probe
Is it still alive?
Kubernetes asks: "Is the application functioning, or is it stuck?"

If it fails repeatedly, Kubernetes restarts the container.


3. Readiness probe
Can it receive traffic?
Kubernetes asks: "Is this application ready to handle requests?"

If it fails, Kubernetes stops routing traffic to that Pod, but doesn't necessarily restart it.

24)In normal circumstances, yes, if the application is functioning correctly inside the container, the container is necessarily running.
25)Remember: Container state tells us whether the container is running; health checks tell us whether the application is functioning as expected.
26)Can the container be marked unhealthy while the application inside it is actually healthy?

Yes, absolutely!

For example:
- Your application works perfectly and responds to normal API requests.
- But your Docker health check runs curl http://localhost:8000/health.
- You accidentally configured the wrong port, or the health endpoint returns an unexpected status code.
- Docker marks the container unhealthy, even though the application itself is functioning.
So remember:

Unhealthy means the configured health check failed. It doesn't necessarily mean the application is actually broken.

Health checks are only as reliable as the checks we define.

40)A vs B: What are we actually choosing?

A. Pull — Collector requests measurements

The collector periodically asks devices for their measurements.
- Centralized control over collection frequency.
- Works with devices exposing polling interfaces (e.g. SNMP).
- Measurements may be delayed until the next polling interval.
- Many requests can create overhead.


B. Push — Devices send measurements

Devices or agents send measurements whenever they collect them or when configured to do so.
- Can provide lower-latency telemetry.
- Avoids repeatedly polling every device.
- Depends on device capabilities and configuration.

46)My recommendation for NetGuard
For our initial architecture:
- Bounded in-memory queue in the collector.
- Asynchronous processing and controlled concurrency.
- Kafka producer publishes events to telemetry.raw.
- Retry/backpressure policy for incoming sources.
- Explicit acknowledgement only after successful Kafka publication, where the source protocol permits it.
Later, if we need stronger protection before Kafka publication, we can consider a durable local spool (for example, a disk-backed queue).

I would not introduce a second Kafka cluster or broker between devices and the collector. That adds infrastructure without solving a clearly identified problem.

48)4. Where should duplicate detection happen?
I agree with your intuition that detecting duplicates early can save resources.

But consider two different objectives:
- Optimization: avoid sending unnecessary duplicates downstream.
- Correctness: guarantee that duplicate delivery doesn't produce duplicate database records or incidents.
The collector can perform some early duplicate filtering, but it shouldn't be our only protection.

For example, the collector might crash after publishing an event to Kafka but before recording that publication. After restarting, it might publish the same event again.

Therefore, downstream consumers must also tolerate duplicates.

The persistence worker could enforce uniqueness using event_id in PostgreSQL.

51)3. Duplicate detection at every stage: is that excessive?
Your concern is valid. We don't want every service implementing its own expensive deduplication database.

The key principle is:

Every component doesn't need to independently store and deduplicate every event. We need idempotency wherever duplicate processing could cause an incorrect side effect.

Let's examine each stage:
- Collector: can filter obvious duplicates, but shouldn't be our only guarantee. Keeping a permanent record of every received event here could be expensive.
- Stream Processor: can avoid repeated work, but it also needs to handle Kafka redelivery. Its deduplication strategy depends on whether processing has side effects.
- Persistence Worker: should enforce uniqueness in the database. This is a strong correctness boundary.
- ML Worker: doesn't necessarily need a separate deduplication database just to run inference twice. But if duplicate predictions create duplicate anomaly events, we need protection at that boundary.
- Incident Worker: must avoid creating multiple incidents for the same underlying anomaly.
Notice the difference: running inference twice wastes CPU; creating two incidents for one anomaly can be a correctness problem.

We can also use Kafka's idempotent producer to prevent certain duplicate writes caused by producer retries, but it doesn't replace application-level idempotency.

So my recommendation is: propagate event_id throughout the pipeline, enforce uniqueness where persistent side effects occur, and add early filtering only when it is worth the complexity.

96)But there's an important architectural question
What happens when a Stream Processor replica restarts?

Its in-memory cache is empty. It needs a way to reconstruct the current metadata before processing events.

A common solution is:
1. Load an initial snapshot of metadata from PostgreSQL.
2. Start consuming changes from the correct point in the change stream.
3. Apply subsequent changes to the cache.
There is a subtle consistency problem here: we must avoid missing changes that occur while the initial snapshot is being loaded.

97)1. First, what is the change stream?
PostgreSQL has a Write-Ahead Log (WAL). It records database changes in sequence.

Imagine these operations:
WAL position	Operation
100	L42 criticality = High
101	L43 criticality = Medium
102	L42 criticality = Low
103	L44 criticality = High

A CDC tool reads the WAL and exposes changes to consumers.

Think of it as a log with positions, not a queue where a message disappears as soon as one consumer reads it.

Important: A replica reading position 102 does not delete position 102. Other replicas can read it too.

This is exactly why your choice B (all replicas independently consume the changes) makes sense.

98)2. The actual problem: snapshot and change-stream synchronization
Let's use a concrete example.

Suppose PostgreSQL initially contains:
L42 → criticality = High
L43 → criticality = Medium


A new replica starts at 12:00.

A naive startup implementation does this:
1. 12:00:00 — Snapshot begins
   
   It reads L42 = High and L43 = Medium.
2. 12:00:01 — Database update
   
   An administrator changes L42 to Low. PostgreSQL records this in its WAL.
3. 12:00:02 — Replica starts consuming
   
   It starts reading from the current end of the change stream, rather than from the position corresponding to the beginning of its snapshot.
The replica now has:
L42 → High     ❌ stale
L43 → Medium


It missed the update because it started reading from the wrong position.

Notice something important: the change was not deleted when it happened. The replica simply didn't ask to read that earlier position.

If it had started reading from the correct earlier position, as you suggested, it would have received the update.

99)3. How robust CDC solves this
A robust CDC snapshot coordinates two things:
- The state of PostgreSQL at a specific WAL position.
- The position from which subsequent changes must be consumed.
Let's say the CDC mechanism establishes position 100.
Timeline of a coordinated snapshot
1. Establish snapshot position: WAL 100
   
   The CDC mechanism identifies a consistent database state corresponding to position 100.
2. Read initial snapshot
   
   The replica obtains L42 = High and L43 = Medium, representing the state at position 100.
3. Changes happen during snapshot
   
   PostgreSQL records:
   - WAL 101: L42 becomes Low.
   - WAL 102: L43 becomes High.
   The CDC mechanism retains these changes for subsequent delivery.
4. Finish snapshot and replay changes
   
   The replica applies changes after position 100, in order.
   - L42 becomes Low.
   - L43 becomes High.
5. Cache becomes ready
   
   The replica now has the current metadata and continues consuming new changes.

Consistent cache
L42 → Low
L43 → High



This is the fundamental idea behind snapshot coordination in tools such as Debezium.

100)But there is a limitation: CDC changes cannot necessarily be retained forever.

If the required position is no longer available, the replica needs to reload a fresh snapshot.
